# Summary

The Doka CLI discards the error payload returned by the API and prints a
hard-coded *"Http Client Error"* string regardless of the actual server
message. The user only sees a generic line such as
`[400 - Http Client Error] - Search items failed`, even though the
server provides a precise message (operator name, character position,
session state, etc.).

For filter-parsing errors specifically, the CLI now reads the position
the server reports and re-displays the DFS (Doka Filter Syntax) with
the offending character highlighted in red and a caret underneath, so
the user can spot the faulty zone at a glance instead of having to
count characters.

# Symptom

A typical run against `item search` with an invalid filter:

```
[400 - Http Client Error] - Search items failed
```

The same call inspected on the server side returns a JSON body of the
form `{"message": "Unknown filter operator at position 12", "context": ["12"]}`,
which is **never displayed** by the CLI.

# Context

All API responses with status `>= 300` are funnelled through the same
HTTP helper in the CLI (`send_request_builder`). That helper builds an
`ApiError` from a static, borrowed string constant
(`HTTP_CLIENT_ERROR.message`) and ignores the response body entirely.

The server consistently returns either:
- a `ContextMessage` (`message` + `context` array) for richer endpoints
  such as item search and build-query, or
- a `SimpleMessage` (`message` only) for most other endpoints.

Both shapes are JSON and deserialisable through types already present
in `dkdto`.

# Root cause

The non-2xx branch of `send_request_builder` short-circuits before
reading the response body. It constructs an `ApiError` using a static
borrowed message and never inspects the payload. This is purely a
display loss; the server-side information exists, the wire is correct,
but the CLI throws it away.

# User impact

- Diagnosing client-side errors requires inspecting the server log,
  which is unavailable to most end users.
- Filter-expression errors, session-expiry errors, validation errors
  and access-control errors all surface as the same opaque message.
- The user wrongly suspects the CLI is wrong, the network is wrong, or
  the syntax is wrong, when the server has already provided a precise
  explanation. The diagnostic loop is longer than it needs to be.
- This was the aggravating factor in [B0001](../B0001-lexer-operator-space/B0001.md):
  the underlying lexer bug would have been obvious in a few seconds had
  the CLI displayed *"Unknown filter operator at position 12"*.

# Scope

- **Affected**: `doka-cli`, the shared HTTP helper used by every API
  call (`search_item`, `get_item`, `create_item`, `add_tag`, login,
  session, file upload/download, etc.).
- **Not affected**: `document-server` and other server-side crates;
  shared `dkdto` types; the wire format. The fix is purely a
  client-side display change.

# Fix direction

Three coordinated changes:

1. **`dkdto::ApiError` gains an optional `context: Vec<String>` field**
   (`#[serde(default)]`, additive) so structured information attached
   to an error (e.g. character position) can survive the trip from
   server to client without being squashed into a string. The static
   `borrowed` constructor loses its `const` qualifier — no caller used
   it in a const context.

2. **`doka-cli::request_client::send_request_builder`** reads the
   response body once on non-2xx and delegates decoding to a new
   `extract_api_error` helper that tries, in order:

   1. `ContextMessage` (richer shape, used by search / build-query);
      both `message` and `context` are preserved on the returned
      `ApiError`.
   2. `SimpleMessage` (default shape on most endpoints).
   3. Raw trimmed text (plain-text or HTML responses).
   4. Static `HTTP_CLIENT_ERROR.message` (empty / whitespace-only
      bodies).

3. **`doka-cli::item_commands::search_item`** renders errors itself,
   in colour, before returning a silent sentinel to its caller:

   - If the filter is known and the server attached a numeric position
     in `context[0]`, the filter is reprinted with the offending
     character in bold red and a caret line underneath, followed by the
     server's message in red. No `[400 - …]` prefix.
   - Otherwise the message alone is printed in red.

   The corresponding branch in `main.rs` stops wrapping the call with
   `eprint_fwd!` (which would print a second, redundant technical
   line) and drops a leftover `dbg!`.

# Tests added

Unit tests for the new helper `extract_api_error`
(`error_extraction_tests`, isolated from the live-stack fixtures of
`mod test`):

- ContextMessage with position context → `message` is preserved
  verbatim and `context` is preserved as a `Vec<String>` on the
  returned `ApiError`.
- ContextMessage with empty context → message verbatim, empty context.
- SimpleMessage → message verbatim, empty context.
- Raw text body → trimmed body, original status.
- Empty / whitespace-only body → static fallback.

# Verification

End-to-end smoke test with the running stack:

1. Reproduce B0001 (filter `(val  > 100)`). The CLI must now display
   the filter with the offending character in red, a caret marker
   below, and the server's *"Unknown filter operator at position N"*
   message in red. The `[400 - Http Client Error]` line must be gone.
2. Run `doka-cli item search -f '[unknown_tag == "x"]'` against a
   collection that does not define `unknown_tag`. The CLI must print
   *"Tag attribute 'unknown_tag' not found in definitions"* in red.
3. Run any command after an expired session. The CLI must now print
   the session-manager's explicit error message in red.
