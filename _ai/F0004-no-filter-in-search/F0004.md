# Goal
The item search API (`GET /document-server/search`) must return **all
items of the customer** when no effective filter expression is provided,
while preserving pagination and `order_tags`. The same semantics apply to
`PUT /document-server/build_query`, which shares the filter-parsing
fallback.

# Gap
Today both delegate entry points coerce a missing filter into the literal
string `"()"` before handing it to the parser:

```rust
// document-server/src/search/search_delegate.rs:66 (search_item)
// document-server/src/search/search_delegate.rs:147 (build_query)
analyse_expression(filter_expression.as_deref().unwrap_or("()"))
```

`"()"` is rejected by the lexer with
`FilterErrorCode::EmptyLogicalOperation` (see
[`filter/filter_lexer.rs`](../../document-server/src/filter/filter_lexer.rs)
around line 704), surfaced as HTTP **400 Bad Request**. The same outcome
occurs for `filters=` (empty string), `filters=%20%20%20`
(whitespace-only), and `filters=%28%29` (explicit `()`).

The disabled regression test
[`doka-api-tests/tests/ut60_api_item_search.rs:99-127`](../../doka-api-tests/tests/ut60_api_item_search.rs)
already documents this gap.

# Inputs
Four equivalent **"no-filter"** forms accepted on the `filters` query
parameter:

| Wire form (`filters=` value)           | After `Option<String>::as_deref()` |
|----------------------------------------|------------------------------------|
| parameter omitted                      | `None`                             |
| empty value (`?filters=`)              | `Some("")`                         |
| whitespace only (`?filters=%20%20%20`) | `Some("   ")`                      |
| explicit empty AST (`?filters=%28%29`) | `Some("()")`                       |

Any non-empty, non-`()` value continues to be routed to
`analyse_expression` unchanged.

# Output
A single SQL `String` of the same shape as the F0003 output, with **no
filter-driven joins** and `WHERE TRUE` as the final boolean clause:

```sql
SELECT i.id,
    name,
    file_ref,
    created_gmt,
    last_modified_gmt
    [, <projected_tag_columns>]
FROM cs_<customer>.item i
[<LEFT OUTER JOIN … for each order_tag>]
WHERE
    TRUE
[ORDER BY
    <order columns>]
```

# Rules

1. **Single normalisation point.** A private helper in
   [`search/search_delegate.rs`](../../document-server/src/search/search_delegate.rs)
   maps the wire input to "no filter":

   ```rust
   fn normalize_filter_input(raw: Option<&str>) -> Option<&str> {
       match raw.map(str::trim) {
           None | Some("") | Some("()") => None,
           Some(s) => Some(s),
       }
   }
   ```

   Both `search_item` and `build_query` route their `filter_expression`
   parameter through this helper.

2. **Sentinel AST — no new variant.** When the helper returns `None`,
   the delegate skips `analyse_expression` and constructs:

   ```rust
   Box::new(FilterExpressionAST::Logical {
       operator: LogicalOperator::AND,
       leaves: vec![],
   })
   ```

   `FilterExpressionAST::MatchAll` is **not** introduced — leaving the
   enum closed avoids ripple changes in every exhaustive match
   (`to_sql_form`, `to_canonical_form`, `extract_all_conditions`).

3. **`WHERE TRUE` emission.** `build_query_filter` in
   [`engine/generator.rs`](../../document-server/src/engine/generator.rs)
   gets one branch:

   ```text
   Logical { leaves: [], .. } → "TRUE"
   ```

   This replaces what would otherwise be the invalid SQL fragment `()`.
   The surrounding template (`WHERE\n    <fragment>`) is unchanged —
   F0004 does not edit `QUERY_FILTER_TEMPLATE`.

4. **Order-tag joins.** `compile_search_query` must build a
   `LEFT OUTER JOIN` for every `order_tag` that is **not** already
   covered by a filter condition, using a synthetic
   `tag_value_filter = TRUE`. With "no filter" + `order_tags=[t1, t2]`,
   the loop synthesises two joins (`ot_t1_0`, `ot_t2_0`) so that
   `ORDER BY ot_t1_0.value, ot_t2_0.value` continues to resolve.

5. **Pagination & projection.** `start_page`, `page_size`, the projected
   tag columns built from `build_select_tags`, and the F0001 / F0002 /
   F0003 escaping rules on non-empty filters are **unchanged**.

6. **Backward compatibility.** A non-empty, parseable filter takes the
   pre-F0004 code path verbatim. No regression on
   `cargo test --test F0003-global-sql-search` is acceptable.

# Errors
- The four no-filter forms **never** return 400 — they return 200 with the item list (possibly empty if the customer has no items, never an error).
- A **malformed** non-empty filter (e.g. `"(unbalanced"`, `"(name = \"x\")"`, …) still returns 400 with the existing
  `FilterError → ContextMessage` contract from [`search_delegate.rs:66-69`](../../document-server/src/search/search_delegate.rs).
  F0004 does not change this branch.

# Examples — wire input to final WHERE fragment

| `filters=` query value     | Internal AST                              | Emitted WHERE fragment                                     |
|----------------------------|-------------------------------------------|------------------------------------------------------------|
| (omitted)                  | `Logical { AND, [] }`                     | `TRUE`                                                     |
| empty                      | `Logical { AND, [] }`                     | `TRUE`                                                     |
| `   ` (whitespace)         | `Logical { AND, [] }`                     | `TRUE`                                                     |
| `()`                       | `Logical { AND, [] }`                     | `TRUE`                                                     |
| `(name == "x")`            | `Condition(name == "x")`                  | `unaccent_lower((tv.value_string)::text) = unaccent_lower('x')` |
| `(unbalanced`              | parser error                              | n/a — 400 Bad Request (unchanged)                          |

# Implementation surface (informative)

The change is confined to three localised edits:

- One helper + one branch in
  [`search/search_delegate.rs`](../../document-server/src/search/search_delegate.rs)
  (reused by `search_item` and `build_query`).
- One branch in `build_query_filter`
  ([`engine/generator.rs`](../../document-server/src/engine/generator.rs)).
- One loop extension in `compile_search_query`
  ([`engine/generator.rs`](../../document-server/src/engine/generator.rs))
  to honour rule 4.

No change to the lexer, normaliser, parser, CLI client, or HTTP route.
